**Requested Roster (5 Agents):**

*   **Role:** Penetration testing and injection prevention.
*   **Function:** Specifically hunts for unprotected I/O operations, environment variable poisoning risks, unsafe deserialization, and missing context managers (`with` blocks) that could lead to zombie processes or database locks.

*   **Role:** Resource management and runtime efficiency.
*   **Function:** Inspects data structures, loop constraints, and SQLite transaction bounds. It should flag expensive full-table scans, memory-heavy array loading, and missing generator paradigms. 

**4. Logical Consistency Judge (The "Blind" Critic)**
*   **Role:** Abstract logic stress-testing.
*   **Function:** This is the core adversarial agent. It must assume absolutely *no* outside context. Given a logic flow, it actively attempts to conceptualize race conditions, off-by-one errors, and state-desyncs. It does not care what the code is *supposed* to do, only how it can technically fail.

**5. Synthesis Director (The Arbiter)**
*   **Role:** Executive summary and remediation formatting.
*   **Function:** Ingests the findings from the previous 4 agents. Its job is to filter out semantic noise and false positives, consolidating the genuine vulnerabilities into a strictly formatted, actionable Markdown ledger.

### Feature Name: TUI State Container & Asynchronous Rendering Architecture
**Abstract:** Decouple the TUI from direct synchronous SQLite queries by implementing an event-driven, in-memory State Container and leveraging Textual's Worker API to eliminate main-thread blocking.
**Date/Time Entered:** 2026-06-30T17:58:20-04:00
**Status:** Unfulfilled

**Description:**
As the Sovereign Datacenter expands and Nexus workflows grow in complexity, the Textual UI can experience rendering latency (frame stutter, slow modal mounts). This is primarily caused by synchronous blocking operations on the main event loop (e.g., massive JSON parsing, deep SQLite queries, or mounting thousands of DOM nodes at once). 
**Proposed Enhancements:**
1. **Polled Database State Objects (State Container):** Build an in-memory buffer (Python dictionaries) that loads SQLite tables in the background. The TUI reads exclusively from this instantaneous memory buffer. The buffer updates via background polling or event triggers when an agent modifies the database.
2. **Textual Worker API (`@work(thread=True)`):** Push heavy processing off the main asyncio thread. Modals should mount instantly with loaders, dispatch a background worker to query data, and populate upon receiving a callback.
3. **DOM Optimization:** Implement lazy-loading or pagination for massive files (like reading the `unified_session_ledger.md`) to prevent the Textual engine from recalculating layout syntax highlighting for thousands of nodes on a single tick.

**Abstract:** A deterministic CI/CD reasoning tool (`omni evaluate-plan`) that mathematically evaluates proposed implementation plans across 5 Oracle vectors and appends a Reasoning Confidence Score (RCS) before review.
**Date/Time Entered:** 2026-07-28T20:04:36-04:00
**Status:** Unfulfilled

**Description:**
As the 5 Specialist Oracles (NetAndClient, OrchestrationAndEngine, TUIAndInterface, ToolsAndRAG, StateAndSovereignty) provide deep, granular codebase auditing, tracking all domain-specific nuances creates exponential cognitive load ($M_{\text{load}} \propto N_{\text{domains}} \times \text{Granularity} \times \text{Dependencies}$). 

This feature introduces an automated reasoning gatekeeper integrated into the `omni` CI/CD toolchain (`omni evaluate-plan`). The tool evaluates proposed plans prior to user presentation and calculates a composite **Reasoning Confidence Score (RCS)**:

$$RCS = w_1 \cdot C_{\text{oracle}} + w_2 \cdot S_{\text{contract}} + w_3 \cdot G_{\text{completeness}} + w_4 \cdot E_{\text{economics}} - w_5 \cdot R_{\text{risk}}$$

**Core Vectors Evaluated:**
1. **Inter-Oracle Consensus ($C_{\text{oracle}}$)**: Measures graph contract alignment across all 5 Oracle domain boundaries.
2. **Static AST & Contract Soundness ($S_{\text{contract}}$)**: Verifies symbol preservation, type safety, and SQLite database schema constraints (e.g. preventing `UNIQUE(job_id, current_node)` collisions).
3. **Intent Delta & Requirement Completeness ($G_{\text{completeness}}$)**: Evaluates plan evolution across iterative versions (v1 → v2 → v3), ensuring core requirements and conceptual refinements discovered during early drafts are not silently dropped as plans progress.
4. **Edge Economics & Hardware Constraints ($E_{\text{economics}}$)**: Probes API rate limits (RPM/TPM), local model VRAM bounds, and SQLite WAL write lock limits.
5. **Unknown-Unknown Risk Penalty ($R_{\text{risk}}$)**: Penalizes un-sandboxed I/O, un-synchronized thread singletons, and unhedged memory zeroing (`ctypes.memset`).

**Ideological Evolution Rationale:**
Logged as a functional synthesis of ideology and evolution—retaining executive human oversight while building deterministic automation rails to automate oversight reliability without ceding ultimate architectural authority.

### Feature Name: A timed-out step does not stop the flow
**Abstract:** `FlowRunner` breaks its step loop on `cancelled` and `stalled` but not on `timeout`; a timed-out step lets the flow continue and the session is still recorded `completed`.
**Date/Time Entered:** 2026-08-30T00:00:00-04:00
**Status:** Deferred (needs decision)
**Verified:** Read directly in `maccre_core/orchestration/flow_engine.py` — both `execute_flow` and `resume_flow` test only `pool_status == "cancelled"` and (since Task A5) `"stalled"`.

**Description:**
This is the same silent-success shape that Task A5 removed for stalls: work does not
finish, and the session reports success anyway. It was deliberately **not** bundled
into A5 because changing timeout semantics is a behaviour change on a shared path and
a timeout is more ambiguous than a stall — it may legitimately mean "needs a longer
budget" rather than "work was lost".

Recommendation: a timed-out step should stop the flow and mark the session `failed`,
matching the stall path. Needs operator sign-off because it will fail flows that
currently report success.

Consequence while unresolved: **`completed` is weaker than it looks**, and anything
enumerating sessions by status — including the Sovereign Importer and any future
spatial map — must not treat it as proof that every step ran.

### Feature Name: `omni` telemetry logger with 30-day semantic compaction
**Abstract:** Give omni a dedicated telemetry log of its own actions that self-compacts every 30 days into an ultra-lightweight abbreviated heuristic, accompanied by an in-file instruction set letting any AI or human semantically re-expand the abbreviations back into full log entries on demand.
**Date/Time Entered:** 2026-08-31T00:00:00-04:00
**Status:** Unfulfilled
**Verified:** N/A — new capability. Explicitly flagged by the operator as **not a priority**.

**Description:**
Goal: a rarely-to-never-read, near-zero-footprint archive that remains losslessly
*interpretable* rather than losslessly *stored*.

**Structure.** The live log file holds two regions:
1. **Recent (< 30 days):** full, verbose entries.
2. **Archive (>= 30 days):** compacted rows in an abbreviated encoding, preceded by
   a **legend and expansion instruction block** — the abbreviation table plus prose
   telling a reader how to reconstitute a full entry from a compacted row.

The expansion contract lives *in the same file as the data*. An archive that needs an
external decoder is one refactor away from being unreadable.

**What to record.** Command, target project, resolved engine, duration, and outcome
per stage: zombies found/terminated, bytecode files removed, caches purged, cache
removal failures, registry entries pruned, Ruff/Pyright pass/fail and durations,
whether `--smart` was used and how many files it scoped.

**Why this is worth having.** Every finding in the 2026-08-30 omni audit —
`omni clean` removing nothing while reporting success, a `wmic` call that had been a
silent no-op since Windows deprecated it, a PID registry grown to 48 entries over two
months — would have been *visible in a trend* rather than requiring a from-scratch
forensic pass. A tool that governs every build should be able to say what it has been
doing.

**Design cautions:**
- Compaction must be **idempotent and crash-safe**. It rewrites the operator's only
  record of tool history; a partial rewrite is data loss. Write-temp-then-atomic-swap,
  as `concurrency.atomic_write_text` already does for MACCRE artifacts.
- The abbreviation table must be **versioned**. A compacted row encoded under v1 and
  read under v2 legend silently misreports.
- Do not compact `build_pipeline.log` in place — that file is protected from
  `omni clean` precisely because it is the existing record. Introduce a separate
  telemetry file rather than mutating it.

**Cross-reference:** overlaps the proposed `omni doctor` (see
`C:\OmniBuilder\omni-proposed-improvements.txt`, NEW ITEM E) — `doctor` reports
present state, this records state over time. `doctor` is the natural producer of the
per-run telemetry record.

### Feature Name: TUI hot-reload of system changes without restart
**Abstract:** Refresh the running TUI to pick up code, agent, MacroNode and topology changes on the fly, instead of requiring a full close-and-relaunch after every system change.
**Date/Time Entered:** 2026-08-31T00:00:00-04:00
**Status:** Unfulfilled
**Verified:** N/A — new capability. Operator-identified as the last blocker to daily-driver use.

**Description:**
Currently every system change requires closing the TUI, which is the dominant
friction in an authoring session.

**Scope this carefully — the valuable 80% is not code reload.** Python module
reloading is genuinely hard and mostly a trap: `importlib.reload()` does not update
already-instantiated objects, does not re-run class bodies for live instances,
breaks `isinstance` against the pre-reload class, and leaves stale references
throughout. A Textual app holds widget instances; the engine holds broker
connections and a thread pool. Attempting general code hot-reload invites a class of
bug far worse than restarting.

What actually changes minute-to-minute during authoring is **not Python code** — it
is agent definitions, the MacroNode registry, topology CSV, prompts and node config.
Those are data, and reloading them is tractable.

**Tiered proposal, cheapest first:**

1. **Config/registry reload (highest value, lowest risk).** Partly built already:
   `TopologyEngine` has `flush_cache()`, a 5 s TTL, `merge_config_overlay` and
   `_reapply_overlays`. Extend that pattern to the agent roster and MacroNode store
   and expose a single explicit "Reload Definitions" action. No process restart, no
   module reload.
2. **CSS / layout reload.** Textual already supports live CSS reload in dev mode;
   surface it rather than reimplement it.
3. **Warm restart with session reattach.** For real Python changes, relaunch the
   process but reattach to the live job — the job lives in `task_queue`, not in
   memory, so the session survives. This is a *restart* that feels like a reload and
   is far safer than reloading modules in place.
4. **True module reload — only for leaf modules with no live instances**, e.g.
   deterministic node handlers looked up per call. Anything holding state is out.

**Hard constraint: never reload mid-flight.** Eight workers may hold locks and
in-flight `TopologyEngine` instances. A reload must either wait for drain or be
restricted to values re-read per node. Reloading a topology under a running scatter
would reproduce the scope-mismatch class of failure found on 2026-08-30, where two
parts of the system disagreed about the same graph.

### Feature Name: Android assistant client — MACCRE as the daily AI interface
**Abstract:** An Android app running from Google Drive that replaces the Gemini app: a personal assistant with swarm-manager capability, invoking hand-built MacroNodes by name from a robust registry.
**Date/Time Entered:** 2026-08-31T00:00:00-04:00
**Status:** Unfulfilled
**Verified:** N/A — new capability.

**Description:**
The end state: MACCRE, not Gemini, is the phone-side assistant. The operator names a
MacroNode aloud or in text and the system knows how to run it.

**Feasible now:** MacroNode invocation by name. `get_macronode_store()` and
`resolve_primitive_node_id()` already provide registry lookup and alias resolution.
A name→MacroNode resolver over the existing store is a small piece of work.

**Two architectural constraints that shape everything else:**

**(a) Do not run MACCRE *from* Google Drive.** A Drive folder is not a filesystem
with locking semantics. SQLite in WAL mode over a sync folder is a corruption
scenario, not a deployment: two writers, or one writer plus a mid-sync read, and the
job queue is gone. This is not theoretical caution — this phase spent three runs on
defects caused by two components disagreeing about shared state on a *local* disk.

**(b) MACCRE is currently Windows-coupled.** The credential vault is Windows DPAPI
via `crypt32.dll` (`maccre_core/orchestration/windows_vault.py`); process management
uses `taskkill` and PowerShell. None of that exists on Android. The vault in
particular needs a platform abstraction before any non-Windows client is possible.

**REVISED 2026-08-31 — the client/server conclusion below was wrong.**

The original text of this entry concluded that the architecture "must be
client/server, not MACCRE on the phone", on the grounds that SQLite over a sync
folder invites corruption from concurrent writers. The operator corrected this: the
design is **deliberately serverless, single-writer** — the same code runs at home and
on the phone, **never at the same time**, with every edge node on a personal cloud.
Eventually the laptop is barely used at all, once the device cluster is networked.
A non-Google VPN-based transport is intended later; Drive is the expedient first
substrate because MACCRE is already Google-centric.

That constraint dissolves the concurrency objection. A generic multi-writer hazard was
substituted for the actual architecture. **Serverless single-writer is sound**, and
this project's dependency discipline is what makes "exact same code everywhere"
credible rather than aspirational — chromadb excised in favour of a SQLite FTS5 store,
openpyxl vendored with a never-reinstall directive, ZMQ and Flet marked dead.

**One narrower objection survives, and single-writer does NOT fix it: WAL mode is
hostile to file sync.**

`PRAGMA journal_mode=WAL` is set in at least eight places (`local_broker.py`,
`sqlite_ledger.py`, `sovereign_store.py`, `telemetry_db.py`, and several
monitors/tests). A WAL database is **three files** that must be mutually consistent:
`.db`, `.db-wal`, `.db-shm`. A sync client uploads files **independently, with
independent timing and independent completion.** On handoff a device can therefore
receive a `.db` from time T alongside a `-wal` from T−30s, absent, or half-uploaded.

This is not a concurrency problem — it is transactional atomicity across a file
*set*. Sequential single-writer access does not help, because sync is not atomic
across multiple files. Outcomes, in order of increasing unpleasantness: SQLite
replays a stale WAL and silently loses the last N transactions; a mismatched `-shm`
prevents the database opening; a partially-uploaded `-wal` yields torn frames.

**Fix — WAL is a concurrency optimisation, and the phone has no concurrency to
optimise:**
1. On clean shutdown run `PRAGMA wal_checkpoint(TRUNCATE)` and close, folding the WAL
   into the main file so only **one** file needs to sync.
2. Better, for a sync-backed datacenter specifically, use `journal_mode=DELETE` so no
   persistent `-wal` ever exists. Keep WAL on the laptop, where eight concurrent
   workers genuinely need it. **A per-deployment setting, not a global downgrade.**

Same primitive as the deferred omni WAL item — checkpoint, never unlink.

**Three smaller constraints:**

**(a) Drive on Android is not a filesystem.** The Drive Android app is a SAF document
provider, not a synced local folder — there is no POSIX path for Python to open.
Drive for Desktop provides a drive letter; Drive for Android does not. The phone
therefore needs a real bidirectional sync client (rclone under Termux, or
DriveSync/FolderSync) materialising files to local storage. Not a blocker, but "Drive
does it" becomes "a sync client does it, Drive is the backing store", and that
client's completeness guarantee becomes load-bearing.

Given the stated intent to move to a non-Google VPN transport, **Syncthing over
Tailscale is a better fit than Drive for this shape** and worth treating as the
target rather than the fallback: whole-folder consistency, explicit conflict files,
no cloud intermediary.

**(b) Mechanise the single-writer rule; do not rely on remembering it.** It is doing
all the safety work. A device lease file in the datacenter root — stable device UUID,
acquired-at, heartbeat, clean-release flag. On startup: un-released with a live
heartbeat means refuse and name the holder; un-released but stale means warn loudly,
because the other device crashed and its sync state may be incomplete.

This is exactly Phase 6.13 Track A's `locked_at` + heartbeat design one level up —
task lease becomes device lease. The PID-reuse lesson transfers too: use a persisted
UUID, never a hostname, because a reusable identifier is worse than no identifier.

**(c) Detect Drive conflict forks.** When Drive does detect divergence it writes
`foo (1).db` rather than merging — a silent fork, invisible until data goes missing.
A startup scan for conflict-named siblings in the datacenter is cheap insurance.

**Android platform blockers — bounded and enumerable:**

| Dependency | Problem |
|---|---|
| `win10toast` | Windows-only; hard import failure |
| `windows_vault.py` | DPAPI via `crypt32.dll`. Gates everything, since it holds credentials |
| `sqlite-vec` | Compiled extension; needs an aarch64/Android build |
| `cryptography` | Rust-based; historically painful under Termux |
| `pyperclip` | Needs `termux-api` for a clipboard backend |

Everything else — `textual`, `requests`, `google-genai`,
`google-api-python-client`, vendored openpyxl — is pure Python and should move as-is.
The credential vault is the real prerequisite; the rest are guards.

**Still feasible now, unchanged:** MacroNode invocation by name.
`get_macronode_store()` and `resolve_primitive_node_id()` already provide registry
lookup and alias resolution.

**Related:** the existing *Local Edge LLM Sync Node (S25 Ultra Integration)* entry
describes an adaptive-interval Drive polling pattern. That remains useful for
**dispatching work to edge devices**, which is a different problem from carrying the
datacenter between devices — worth keeping the two separate.

### Feature Name: Sovereign local model cluster (de-bloated Samsung compute fabric)
**Abstract:** A cluster of de-bloated Samsung devices (S24 Ultra, S25 Ultra, S25 and spares) providing local inference compute and VRAM over a high-speed USB hub bridged to ethernet; each device runs models in its own semantic memory datacenter named as a MACCRE extension, swapping in for node roles that can be handled locally, with large models sharded across the network link.
**Date/Time Entered:** 2026-08-31T00:00:00-04:00
**Status:** Unfulfilled
**Verified:** N/A — new capability. Hardware acquisition in progress.

**Description:**
This decomposes into two very different propositions with very different odds.

**The strong half: role-sharded small models, one per device.** This is the right
idea and it fits MACCRE's architecture almost exactly. MACCRE already assigns work
per *node*, each node is an independent bounded task, and a scatter runs eight of
them concurrently. Handing individual node roles to individual devices is
embarrassingly parallel — no inter-device bandwidth needed beyond payload transfer,
no synchronisation, and a device failure degrades one lane rather than the flow.
Budget realistically: S24 Ultra ships 12 GB RAM, S25 Ultra 12–16 GB, leaving perhaps
4–8 GB usable after the OS — roughly one quantised 7–8 B model per device. Three or
four devices therefore gives three or four concurrent local agents, which is a real
and useful fraction of an eight-wide scatter.

**"Semantic memory datacenters named as extensions of MACCRE"** maps cleanly onto the
existing `__DATACENTER/<project>/` layout — a per-device namespace is a per-device
project root. No new concept required.

**The weak half: sharding a large model across the cluster.** Be sceptical here.
*Tensor* parallelism — splitting individual layers across devices — requires
NVLink-class bandwidth and microsecond latency; over USB 3 or gigabit ethernet the
per-token activation exchange dominates and you get seconds per token, not tokens per
second. *Pipeline* parallelism (device 1 holds layers 1–N, device 2 holds N+1–M) is
far more tolerant of a slow link, because only activations cross the boundary once
per stage rather than many times per layer. If large-model sharding is attempted, it
should be pipeline-parallel, and throughput will be bounded by the slowest stage.

**Two practical limiters that will bite before bandwidth does:**
- **Thermal throttling, not VRAM, is the real ceiling.** Phones are built for bursty
  loads. Sustained inference throttles hard, and a swarm scatter is sustained by
  definition. Plan for active cooling and expect steady-state throughput well below
  burst benchmarks.
- **Bootloader lock.** Meaningful de-bloating needs an unlocked bootloader; US-market
  Samsung flagships generally ship locked. This is a procurement constraint, not a
  software one — worth confirming per device before buying spares.

**Recommended sequence:** one device, one role, one model, measured end to end
against the current cloud path first. The interesting number is not tokens/sec — it
is whether a local 7 B model is *good enough for a specific node role*. If it is,
this scales beautifully. If it is not, no amount of cluster engineering fixes it.
This also composes with the existing *Local Edge LLM Sync Node* entry, which is the
natural first integration point.

### Feature Name: AI Studio KnowledgeStore — pinned, not embedded; isolated by default
**Abstract:** AMENDMENT to the *AI Studio conversation corpus* entry above. **Verified:** Existing pattern confirmed — `maccre_core/.../sovereign_store.py` implements `SovereignPinStore` as a `pins` table plus a `pins_fts` FTS5 virtual table with BM25 ranking. `knowledge_store.py` uses the same FTS5/BM25 approach.

next step received a 59-byte stub instead, because the step boundary read the wrong
path. The merge's *lineage* broke. Provenance and payload lineage are the same
problem viewed from two ends, and fixing E1/E2 is therefore the first concrete
increment of this doctrine rather than unrelated work.

**Three properties to build in from the start:**

1. **Append-only.** Provenance and trust history are never overwritten. Overwriting
   makes "why is this trusted" unanswerable, which is the only question that matters
   during an audit.
2. **Survives aggregation.** A derived artifact's provenance is the union of its
   inputs', plus the transformation that produced it.
3. **Externally distinguishable.** An agent reading a ledger must be able to tell
   MACCRE's own established output from imported external material, without inferring
   it from context.

**Related:** Phase 6.13 spent three rounds on a defect where two parts of the system
disagreed about the same identifier, and the lesson generalises exactly here — an
identifier that is approximately right is worse than one that is absent, because
downstream logic acts on it. A provenance tag that is *plausible but wrong* is worse
than no tag at all.

### Feature Name: CrumbRunner — provenance and trust agent for scoped knowledge ingestion
**Abstract:** A dedicated low-temperature systems agent that assembles "crumb-tracks" — portable manifests of scoped knowledge drawn from anywhere inside or outside the system — hands them to any agent for a task, assigns trust scores audited through the OSINT pipeline, and performs knowledge reconciliation and conflict tracking whose results apply epigenetically to trust.
**Date/Time Entered:** 2026-08-31T00:00:00-04:00
**Status:** Unfulfilled
**Verified:** N/A — new agent. Operator has been developing the concept for some time.

**Description:**
CrumbRunner is the enforcement mechanism for the provenance doctrine above, and the
knowledge-scoping front end of the automated OSINT pipeline at ingestion.

**Low temperature is correct and worth stating as a constraint.** This is an
extraction, attribution and bookkeeping role. Any creative latitude here manufactures
citations, which is the precise failure the agent exists to prevent. It should be
among the most deterministic agents in the roster.

**A crumb-track is an artifact, not agent state.** "Give it to any agent for a task"
means it must be a portable, serialisable manifest — source list, scope boundaries,
trust scores, reconciliation notes, timestamps — that any agent can be handed and any
human can read. That also makes it independently testable, which agent-internal state
would not be.

**"Epigenetic" trust maps onto a concrete and rather elegant model:** an append-only
event-sourced score. A source carries an **intrinsic base trust** that is never
mutated. Reconciliation events, corroborations and conflicts append **contextual
modifiers**. Effective trust is computed from base plus accumulated modifiers at read
time. So trust is expressed differently in different contexts without the underlying
source record ever being rewritten — and the full history remains auditable, which
satisfies the append-only property above.

**Four trust hazards that must be designed against, not discovered:**

1. **Score laundering — the most important one.** A low-trust source summarised by a
   high-trust agent must not inherit the agent's trust. **Rule: an output's trust is
   bounded above by the minimum trust of its inputs.** Trust is a ceiling inherited
   from provenance, not a label applied by the last handler. Without this rule,
   laundering happens automatically, silently, and on every summarisation.
2. **Circular corroboration.** If A cites B and B cites A, naive corroboration
   inflates both indefinitely. A crumb-track is a directed graph, so cycle detection
   is required before corroboration can raise a score — and
   `maccre_core/orchestration/topology_graph.py` already provides edge building and
   reachability over exactly this shape. Reuse it rather than writing a second graph
   implementation; two representations of one graph is a failure mode this codebase
   has already produced twice.
3. **Staleness.** A trust score computed against a live web source six months ago is
   not a current statement. Every score needs an as-of timestamp, and either decay or
   a re-audit trigger. A confidently stale score is worse than an absent one.
4. **Silent conflict resolution.** When two sources disagree, CrumbRunner must
   **record the conflict and both positions** and surface it to the consuming agent —
   never collapse it to a single value. Picking a winner silently reproduces the exact
   shape of the tether defect: one confident value where the system actually held two
   incompatible ones.

**Scope boundary worth fixing early:** CrumbRunner assembles and scores. It does not
*decide* on the operator's behalf. Reconciliation output is evidence handed to a
consuming agent or to the operator, not an adjudication.

**Related:** the *AI Studio KnowledgeStore* entry is CrumbRunner's first external
source and its natural pilot — a bounded, offline, already-cleaned corpus with a known
provenance story, which makes it a far safer first target than live web ingestion.

### Feature Name: Containerized session archive with full system-wide telemetry snapshot
**Abstract:** Every completed session becomes a single fingerprinted, heavily compressed, quick-to-open container holding the entire MACCRE telemetry snapshot for that session; sessions are loaded from the Session Manager only as templates and never re-run, so the container is the immutable record, stored beside the unified ledger in `04_Code_Artifacts` and daemon-tracked for integrity.
**Date/Time Entered:** 2026-08-31T00:00:00-04:00
**Status:** Unfulfilled
**Verified:** N/A — new capability. Operator-specified as a prerequisite for re-enabling cross-project memory.

**Description:**
The archive *is* the completed session. Requirements as stated:

- **Full telemetry, system-wide.** Not the session's own events — the entire MACCRE
  telemetry state during that session.
- **Fingerprinted**, and registered in the database.
- **Heavily compressed**, but **quick to open and close** — inspectable without
  unpacking a tree.
- **Containerized as one file**, so a user can inspect a whole session in one place.
- **Stored in `04_Code_Artifacts` for the project**, alongside the unified session ledger.
- **Daemon-tracked for integrity** after the fact.

**The immutability rule is what makes this coherent, and it deserves its own emphasis:**

> Sessions are loaded from the Session Manager **only as templates.** A run always gets a
> new `sessionID`. **A session is never run a second time.**

That single constraint is what permits containerisation at all. A mutable session could
not be sealed, fingerprinted or integrity-checked, because any of those would be
invalidated by the next run. It also means the container is a genuine historical record
rather than a cache — which is the property the provenance doctrine needs.

**Engineering notes:**

- **Format choice is load-bearing given "quick to open/close yet compressed".** A solid
  archive (`.tar.zst`, `.tar.xz`) compresses better but requires decompressing a stream
  to reach one member. A per-member-compressed container (`.zip` with deflate/zstd) gives
  random access to individual entries at a modest ratio cost. **Recommendation: per-member
  compression.** Inspectability was stated as a requirement; a solid archive trades it
  away for a ratio nobody asked for.
- **Fingerprint the members, not only the container.** A container hash detects that
  *something* changed; per-member hashes plus a manifest identify *what*. The manifest is
  also what makes selective inspection possible without trusting the whole file.
- **Seal on the session's terminal transition, not on a timer.** MACCRE now has four
  terminal states — `completed`, `cancelled`, `failed` (which since Task A5 also covers
  stalled), and the open `timeout` question. **A stalled session's artifacts are
  incomplete by definition**, so its container must record that it is a partial record
  rather than presenting as whole.
- **Do not seal a session whose lineage is broken.** Defects E1/E2 are open: an 8-lane
  merge received eight copies of one document, and a merge's output did not cross the step
  boundary. Containerising that would preserve a hole with a fingerprint on it, which is
  worse than not containerising it.
- **Watch the WAL interaction.** Telemetry databases run `journal_mode=WAL`. A snapshot
  taken while a `-wal` holds uncheckpointed frames captures an inconsistent state. Run
  `PRAGMA wal_checkpoint(TRUNCATE)` before snapshotting — the same primitive already
  required for the omni WAL item and the synced-datacenter work.

**Related:** *Session Manager Dashboard*, *Unified Welcome & Session Selection Screen*
(sessions loaded as templates is a Session Manager behaviour), *System-wide provenance
doctrine*, and the *Session Manager / File Cabinet alignment* contract — an importer
enumerating sessions will want to know that a container exists and what it guarantees.

### Feature Name: Cross-project memory (Synaptic Bridge) — staged re-enablement
**Abstract:** Cross-project semantic memory is deliberately shunted and off by default. Define the conditions for re-enabling it, and stage that re-enablement so the capability arrives when its safety property is satisfiable rather than when every adjacent capability is finished.
**Date/Time Entered:** 2026-08-31T00:00:00-04:00
**Status:** Deferred (needs prerequisite)
**Verified:** Reproduced. `_verify_synaptic_bridge()` in `maccre_core/tools/rag_tools.py` reads `get_datacenter_path("project_schema.json")` and returns `False` when absent; the file exists nowhere under `__DATACENTER`, so `query_foreign_memory()` always denies. **Fails closed — correct behaviour.**

**Description:**
The operator's stated gate for re-enabling, verbatim in substance: full telemetric
coverage of concurrent multi-step flows via the containerized session archive; provenance
nailed down from ingestion to the point an agent sees it, in Sovereign Importer and its
MACCRE File Cabinet bridge; and provable provenance at that level with semantic memory
siloed within a project.

**Assessment, offered because the operator explicitly invited it — the gate should be
split.**

The three conditions are not equally load-bearing for *safety*, because they deliver two
different guarantees:

| Guarantee | Delivered by | Nature |
|---|---|---|
| A cross-project read cannot silently contaminate the reader | chunk-level provenance + trust ceiling + ledger-visible crossing | **read-time constraint** |
| A cross-project read can be reconstructed and proven after the fact | containerized session telemetry archive | **audit-time capability** |

What makes a cross-project read *safe* is the read-time property: the returned chunk
carries its origin project, the consuming agent's output trust is bounded above by the
minimum trust of its inputs, and the crossing appears in the ledger. That is Epoch 4 work
— the provenance doctrine, the trust ceiling, and CrumbRunner.

The session container delivers something genuinely valuable but different: the ability to
*prove afterwards* what happened. Gating a read-time safety property on an audit-time
capability delays the feature by an epoch or more for a reason that does not structurally
hold.

**The counter-argument is legitimate and should be recorded:** if the thesis is
"provenance you can stand behind", read-time labelling is a weaker claim than full
reconstruction. A conservative operator building a trust system has good reason to prefer
the stronger claim before opening a boundary.

**Recommended resolution — two stages, which satisfies both positions:**

- **Stage 1, at the end of Epoch 4.** Re-enable, but **opt-in per query, never globally
  on**, with the trust ceiling enforced, the origin project attached to every returned
  chunk, and the crossing logged in the ledger. Blast radius is one query, bounded and
  recorded.
- **Stage 2, after the containerized session archive.** The container upgrades the
  guarantee from *auditable at read time* to *reconstructable after the fact*. Only then
  does a default-on or broadly-permitted mode become defensible.

This gets the capability roughly an epoch earlier without weakening the trust story,
because opt-in-and-logged is a materially smaller exposure than default-on.

**Independently of scheduling: harden the breaker now.** See the next entry. The current
"off" state is weaker than intended, and that is a correctness question about today
rather than a question about when to re-enable.

### Feature Name: Harden the Synaptic Bridge breaker — make "off" explicit and operator-owned
**Abstract:** Cross-project memory is currently disabled by the *absence of a file*, and the file can be created — and a foreign project whitelisted — by any agent granted the `link_projects` tool. The breaker's switch is on the agent side of the boundary it exists to enforce.
**Date/Time Entered:** 2026-08-31T00:00:00-04:00
**Status:** Unfulfilled
**Verified:** Reproduced by reading source. Three findings below, each cited.

**Description:**
The breaker works today. Three properties make it more fragile than the design intends.

**(a) "Off" is implicit — enforced by a missing file.** `_verify_synaptic_bridge()` returns
`False` because `project_schema.json` does not exist. An implicit breaker is
indistinguishable from a bug when read cold: this was initially misdiagnosed as a dead
feature during the 2026-08-31 archaeology pass, which is the failure mode in miniature.

**(b) The mechanism silently changes once `initialize_workspace` runs.** That function
writes `project_schema.json` with `{"linked_projects": []}`. A CLI-provisioned project
therefore *has* the file, and "off" shifts from *file absent* to *list empty*. Both still
fail closed, so there is no hole — but two different mechanisms enforce the same state,
and only one of them is the one anybody has tested. This matters more now that Sovereign
Importer is expected to call `maccre new` to provision projects: every SI-provisioned
project will have the file.

**(c) `link_projects` is agent-callable, and it closes the breaker.** It is registered in
`TOOL_DISPATCHER` (`maccre_core/tools/tool_registry.py:163`). Its body creates
`project_schema.json` when absent — **at the project root, exactly the path the reader
checks** — and appends to `linked_projects`. So a single tool call by any agent whose
`Tools_Allowed` includes it turns cross-project memory on for that pair, with no operator
involvement.

Access is gated per-agent by `Tools_Allowed`, so this is not universal. But for a system
whose thesis is that probabilistic intelligence must be gated **deterministically**, a
breaker an agent can close is the wrong shape regardless of how narrowly the tool is
granted.

**Recommended:**
1. **Make the breaker explicit and operator-owned** — a single named setting outside
   agent reach, defaulting to disabled. `_verify_synaptic_bridge` consults it *first* and
   returns `False` before touching any schema file.
2. **Remove `link_projects` from `TOOL_DISPATCHER`**, or make it require the elevated
   PIN path that already exists in the 3-tier access-control model. Whitelisting a
   foreign project is an operator act.
3. **Resolve the writer-path divergence.** `link_projects` writes the project root, which
   the reader uses; `sheet_parser` writes `02_Dynamic_Context/project_schema.json`, which
   it does not — and only `if parsed.linked_projects`. Two writers, two paths, one
   reader. Pick the canonical location. This is the same two-representations pattern that
   produced the node-ID divergence and cost three live debugging rounds on the tether.

**Priority note:** this is small, and it is about the integrity of a boundary that is
*currently* relied upon. It should not wait for the re-enablement schedule in the previous
entry.

the Kiro/Antigravity pattern: capability plus judgement, not a command vocabulary.

**What exists to build on.** `Tools_Allowed` already provides a per-agent static grant,
and `TOOL_DISPATCHER` (`maccre_core/tools/tool_registry.py`) already maps names to
callables. That is the foundation and it is **not sufficient** — a static per-agent grant
cannot express "allowed, but confirm first", which is the whole substance of a greylist.

**Tool description hygiene is part of this feature, not adjacent to it.** Evidence from
2026-08-31: `nexus_agent.py:220` advertises *"Searches the semantic thought_pins.db of a
specific project"* — a store that is deprecated and being removed. A tool description
naming a dead capability will have an agent reaching for it, and the resulting failure is
opaque to both the agent and the operator. **The reasoning layer's quality is bounded by
the accuracy of what it is told the tools do.** Auditing every description against actual
behaviour is a required part of this work.

**Honest scoping note:** the harness can expose, bound, and audit. Whether the model
*chooses* well is a function of the model and the descriptions, not the harness. Do not
expect the harness to fix poor selection; expect it to make poor selection **visible and
survivable**.

### 2. The trust-earning inspection routine

A user training routine in which the operator inspects the actions and tool calls an agent
takes — closely modelled on the Kiro/Antigravity coding loop — and through that inspection
develops both trust and the policy that encodes it.

**Design point that matters: trust must be granted per tool *and scope*, not per tool.**
`write_file` into `04_Code_Artifacts` is a materially different act from `write_file` into
`02_Dynamic_Context`, where the databases live. A policy keyed on tool name alone will
either be too permissive to be safe or too restrictive to be useful, and the operator will
route around it. Key the policy on `(tool, scope)`.

**Second design point: the inspection record is provenance.** Every action taken, its
arguments, its outcome, and whether it was auto-approved or confirmed — that is a custody
chain over the assistant's own behaviour, and it should use the same append-only
provenance machinery as the *System-wide provenance doctrine* entry rather than a
private log.

### 3. Whitelist / blacklist / greylist

The deterministic bound on autonomous choice.

| List | Meaning |
|---|---|
| **Whitelist** | May act alone |
| **Greylist** | May propose; requires explicit confirmation before acting |
| **Blacklist** | May not act, and may not propose |

**This is the mechanism a live MACCRE finding already needs.** On 2026-08-31 it was
verified that `link_projects` — which creates `project_schema.json` and whitelists a
foreign project, thereby closing the Synaptic Bridge breaker — is registered in
`TOOL_DISPATCHER` and is therefore agent-callable. See *Harden the Synaptic Bridge
breaker*. That tool is the archetypal blacklist member: an operator act that an agent can
currently perform. **The harness is not only an assistant feature; it is the enforcement
layer that class of problem requires.**

**Build on the existing 3-Tier Access Control and PIN Elevation model** rather than
inventing a parallel permission system — a second representation of one permission
boundary would drift, which this codebase has demonstrated twice.

### 4. Boundary — limited-admin over the MACCRE datacenter only

The fully realised assistant reaches **only** files inside the MACCRE datacenter, as a
**limited administrator**:

- **No deletion.** Removal is a move to a **GLOBAL trashcan**, never an unlink.
- Comparable restraint on other irreversible operations.

**The Archive Trash Protocol already exists** (audited under State & Sovereignty as
*Archive Trash Protocol & Deletion Safety*). Use it; do not build a second trashcan.

Recommended additions: the trashcan is GLOBAL-scoped, so a restore must know which project
an item came from — record the origin path, project, and timestamp on the moved item, or
restore becomes guesswork. And trashcan entries should be fingerprinted on the way in, so
a restore can prove the item is unmodified.

### 5. Boundary — Sovereign Importer is a human gate with no agentic control

> **Sovereign Importer will be used as the user gate for data, with no agentic control.**

Nexus Copilot does not operate the gate. It cannot ingest, cannot tag, cannot push, cannot
mark off-limits. The operator does all of it.

This is what makes the sovereignty model coherent rather than decorative. Sovereign
Importer is the deterministic firewall between MACCRE and everything external; a gate
operable by the probabilistic system it constrains is not a gate. It also means the
assistant's usefulness is deliberately capped at the datacenter boundary — an accepted
cost, and the same acknowledged asymmetry recorded in the *Android assistant client*
entry.

### 6. Android deployment naming

- The MACCRE Android application is **MACCRE Production Center (MACCRE PC)**.
- **Sovereign Importer is also to become an Android app**, running alongside MACCRE PC as
  the data gate.

The assistant identity itself still needs its non-infringing name — see *Rename Nexus
Copilot before any public artifact*, and note that under this entry the name becomes
**user-facing product identity on a shipped mobile app**, which raises the cost of
deferring it further.

### Sequencing

This entry gates the Android work and is gated by very little, which makes it unusually
schedulable:

```
Tool description audit  (small, immediate, independently valuable)
  -> (tool, scope) policy model + greylist confirmation path
    -> inspection/approval surface reusing the provenance ledger
      -> limited-admin enforcement over the datacenter, via the Archive Trash Protocol
        -> earned-autonomy policy accumulated through use
          -> MACCRE PC on Android, with Sovereign Importer as the human gate
```

The **tool description audit is worth doing now**, independent of everything else: it is
small, it directly improves current agent behaviour, and `thought_pins.db` is proof there
is at least one wrong description in the surface today.

**Related:** *Android assistant client*, *Rename Nexus Copilot before any public
artifact*, *Harden the Synaptic Bridge breaker*, *System-wide provenance doctrine*,
*Nexus Copilot Sovereign Sandbox Enhancement* (whose sandbox-execution half was deferred —
this harness is the bounding mechanism that would make it safe, and supersedes the
ungoverned version of it).

### Feature Name: Fan-in gathers the shared session ledger instead of each lane's own output (E1)
**Abstract:** Under `Payload_Mode = "Unified Ledger"` every scatter lane's queue row recorded the shared session ledger as its output, so `CTRL_MERGE` gathered one file N times and reported `Merged 8 sources` over eight identical sections.
**Date/Time Entered:** 2026-08-31T04:14:00-04:00
**Status:** COMPLETED
**Completed:** 2026-09-01T07:05:00-04:00
**Verified:** Reproduced. Observed live on run `job_20260831-041428-6goe`, then reproduced
in code and pinned by a test that **fails when the fix is reverted** — reverting
`get_completed_payload_paths` to read `payload_path` makes three tests fail with all eight
lanes reporting `unified_session_ledger.md`, the exact live signature.
**Completion Metric:** `omni qa` PASS (whole project, per `pyrightconfig.json`); pytest
**703 collected / 703 passed** (665 baseline + 38 new in `tests/test_payload_lineage.py`);
`omni smoke` ALL CHECKS PASSED. Before/after, asserted by test: an 8-lane gather returned
**8 paths / 1 distinct** and now returns **8 paths / 8 distinct**, with the shared session
ledger absent from the result set. `_handle_merge`'s reported count is now the number of
**distinct** sections written, and a collapse emits a WARNING naming the shortfall.
Artifact: `.oracle_artifacts/2026-09-01_e1_e2_payload_lineage.md`. Branch
`phase/6.13-track-a-d-and-payload-lineage`.

**Description:**
The chain was five links long and **only the second was the root cause**:

1. a lane finishes; the worker sets `routing_payload_path` to that lane's own ledger,
   `<node>_<row_id>.md`
2. the Unified Ledger branch in `swarm_worker.execute_cycle` **replaces** it with
   `unified_session_ledger.md`, because that is what the *successor* should read. Correct
   for routing — and it discarded the only reference to what the lane produced
3. `route_task` wrote the routing payload onto the row it was closing, so the row stopped
   recording the lane's output
4. `get_completed_payload_paths` asked "what did each predecessor produce", read
   `payload_path`, and got one path eight times
5. `_handle_merge` built a section per path and logged `Merged 8 sources` — literally
   true, semantically empty, eight identical `## Source: unified_session_ledger` headings

**Correction to the handover, recorded because it matters for the next reader.** The
handover attributed this to link 3 and suggested "a smarter query may not be enough; an
`output_path` column may be needed." Directionally right, mechanically wrong: the lane's
own path is already gone before `route_task` is called, so a column alone would have
faithfully stored the shared ledger. Both had to change.

**What was done.** `task_queue` gained an `output_path` column (CREATE TABLE body plus an
`ALTER TABLE` migration line, following Task A1's `locked_at` idiom). `route_task` takes
and records it at both UPDATE sites, using
`output_path = CASE WHEN ? = '' THEN output_path ELSE ? END` so an empty argument can
never blank a record another caller earned. `get_completed_payload_paths` reads
`COALESCE(NULLIF(output_path,''), payload_path)`. The worker now captures
`node_output_path` **before** the Unified Ledger swap. `_handle_merge` and `_handle_concat`
de-duplicate their inputs and report a collapse loudly.

The fallback to `payload_path` is **load-bearing, not a legacy shim**: `macro_factory`'s
ephemeral spawn and FAILED routes, and the `CTRL_PAUSE` resolver, legitimately never supply
an output because for them the routing payload *is* the passthrough output. It also keeps a
session resumed across this change readable.

**Two things deliberately not changed.** The Unified Ledger branch reads the *successor's*
`payload_mode` rather than the completing node's — that is correct, since payload mode is a
property of what a node wants to *receive*, and it is recorded here only because it reads
like a bug. And `Payload_Mode` remains a bare string literal duplicated across
`topology_engine`, `swarm_worker`, `flow_engine`, `macro_factory`, `admin_tools` and
`nexus_plex`; there is no enum. Introducing one touches all six and was out of scope.

**Doctrine.** This is principle 3 (`Merged 8 sources` was true and meaningless) sitting on
top of principle 5: the query's docstring *stated* the assumption that turned out to be
false — "the completed row is the authoritative record of what that node produced" — with
no test that would fail when it went false. The docstring now records what that reasoning
cost.

**Related:** *Interactive Node Configuration Modal* — per-node Payload Mode is the lever
behind this defect, and making it authorable turns an invisible engine default into a
visible choice. *System-wide provenance doctrine* — this is a lineage break, not adjacent
work.

### Feature Name: A step's output does not cross the step boundary (E2)
**Abstract:** `_find_final_ledger_path` globbed the job's ledger directory and returned the newest `.md` by mtime, so the next step received `CTRL_MERGE_S0`'s 59-byte ledger stub instead of the 426 KB merged document it had just produced.
**Date/Time Entered:** 2026-08-31T04:14:00-04:00
**Status:** COMPLETED
**Completed:** 2026-09-01T07:05:00-04:00
**Verified:** Reproduced. Observed live on run `job_20260831-041428-6goe` (the following
step consumed 59 bytes at a billed $0.000046), then reproduced in a test that **fails when
the fix is reverted** — reinstating the mtime glob makes
`test_a_newer_stub_on_disk_does_not_win` select `CTRL_MERGE_S0_93.md` over
`CTRL_MERGE_S0_merged.md`, the same two filenames as the live run.
**Completion Metric:** `omni qa` PASS (whole project); pytest **703 collected / 703
passed**; `omni smoke` ALL CHECKS PASSED. The defective helper is **deleted**, not merely
bypassed, and a test asserts `FlowRunner` no longer has it and that neither step loop
globs. Artifact: `.oracle_artifacts/2026-09-01_e1_e2_payload_lineage.md`.

**Description:**
`_find_final_ledger_path` promised, in its own docstring, "the final expected artifact path
for the DAG". It delivered the newest file by mtime. Four faults, only the first of which
was in the handover's diagnosis:

1. **It was not a race it sometimes lost — it is one it always lost.** `_handle_merge`
   writes the artifact, then the worker writes the node's ledger stub *after* the handler
   returns. The stub therefore always has the newer mtime.
2. **It accepted `topology_rows` and never read them.** The "final node of the DAG" was
   never consulted; the parameter was dead.
3. **Its scope was the job, not the step.** A step-2 lookup could return a file step 1
   wrote.
4. **`*.md` matched non-payloads** — `thoughts_and_tools_*`, scatter chunk files, and the
   `_merged.md` artifact all live in one directory.

Meanwhile `topology_graph.terminal_nodes()` already existed, with a test asserting
`terminal_nodes(scatter_rows(8)) == ["CTRL_MERGE"]`. The engine had the answer available
and was guessing anyway.

**What was done.** The helper was deleted and replaced by `_find_terminal_nodes` — the
mirror of `_find_starting_nodes`, reading `terminal_nodes()` and hydrating through the same
`f"{node}_S{idx}"` expression the engine uses everywhere — plus `_capture_step_output`,
which asks the queue what that node recorded. All three call sites (both resume paths and
`execute_flow`) now use it.

**Decision recorded: no silent fallback.** When nothing is found, `_capture_step_output`
returns `None`, the caller leaves `current_payload` unchanged and logs at ERROR. Keeping the
glob as a fallback was rejected — a silent retreat to the defective path means the defect
can return with the suite green. Failing the flow outright was *also* rejected, because
that is the same shape as the open *A timed-out step does not stop the flow* decision and
belongs to the operator, not the agent. Carrying the previous payload forward is wrong but
**visible**, which is the distinction principle 2 draws. If the operator prefers a hard
failure here, it is a one-line change plus a terminal-status decision, and it should
probably be made at the same time as the timeout one.

**Decision recorded: divergent terminals resolve by declared topology order.**
`terminal_nodes()` can return more than one node. Ordering by completion time or mtime
would hand the next step a different document on each run. The log states plainly that this
is a choice rather than a fact and suggests authoring a `CTRL_MERGE` if the next step needs
all of them.

**Doctrine.** Principle 4 — the deletion is the point. Two ways to answer "what did this
step produce" is how the TUI and the engine came to disagree about node ids, so the glob
was removed rather than left available to a future call site. Principle 6 — no test
anywhere referenced `_find_final_ledger_path`; the step boundary had zero unit coverage,
which is why a 665-test suite was green over it.

**Related:** *System-wide provenance doctrine* — the planning map names this as the
doctrine's first concrete increment, and it is: the merge's lineage broke. *A timed-out
step does not stop the flow* — shares the terminal-state question above.
